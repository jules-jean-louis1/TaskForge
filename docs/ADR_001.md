# 1. Utiliser Go/Gin pour le backend et Angular pour le frontend

Date: 2026-07-28

## Status

Accepted

## Context and Problem Statement

TaskForge est une application interne de gestion de tickets d’incidents à réaliser en 2 semaines dans le cadre d’un projet solo.

Les contraintes principales sont les suivantes :

- délai court ;
- besoin d’un MVP fonctionnel ;
- déploiement simple via Docker ;
- architecture lisible et maintenable ;
- faible charge utilisateur attendue ;
- besoin de sécuriser l’accès via authentification et rôles ;
- besoin d’un frontend structuré pour une application métier.

Plusieurs technologies étaient envisageables pour le backend :

- Node.js ;
- Python ;
- Go ;
- Rust.

Plusieurs technologies étaient envisageables pour le frontend :

- React ;
- Angular ;
- Svelte.

## Decision Drivers

Les critères de décision retenus sont :

- rapidité de développement ;
- simplicité de maintenance ;
- lisibilité du code ;
- facilité de déploiement en conteneur ;
- cohérence avec un projet MVP ;
- compatibilité avec les besoins fonctionnels du projet.

## Considered Options

### Backend

- Node.js
- Python
- Go
- Rust

### Frontend

- React
- Angular
- Svelte

## Decision Outcome

### Backend: Go with Gin

Go a été retenu pour le backend, avec le framework Gin.

### Frontend: Angular

Angular a été retenu pour le frontend.

## Rationale

### Why Go for the backend

Go est un bon choix pour une API REST de taille modeste car il apporte :

- une syntaxe simple et lisible ;
- une bonne performance ;
- une compilation en binaire unique, pratique pour Docker ;
- un bon support pour le développement d’API ;
- une base solide pour structurer le code en couches.

Dans le contexte de TaskForge, la performance brute n’est pas le critère principal, mais Go reste un bon compromis entre simplicité, robustesse et facilité de déploiement.

Gin a été choisi comme framework web car il permet de construire rapidement une API REST claire, légère et bien structurée.

### Why Angular for the frontend

Angular a été retenu car il fournit un cadre de développement très structuré, particulièrement adapté à une application métier.

Ses avantages dans ce contexte sont :

- organisation claire des composants et services ;
- conventions fortes qui réduisent les choix d’architecture ;
- maintenabilité sur un projet solo ;
- adéquation avec une interface métier comportant formulaires, listes, filtres et dashboard.

Pour un projet de délai court, Angular aide à garder une base de code cohérente et lisible.

## Positive Consequences

- Le backend est basé sur une technologie rapide à déployer et simple à conteneuriser.
- L’architecture du projet reste claire et séparée en couches.
- Angular facilite la structuration du frontend.
- Le projet est plus facile à documenter, tester et présenter.
- La stack choisie est adaptée à un MVP interne.

## Negative Consequences

- La courbe d’apprentissage peut ralentir la livraison si certaines parties de Go ou Angular ne sont pas maîtrisées.
- La stack impose un minimum de rigueur architecturale pour rester lisible.
- Le développement peut être plus long qu’avec une technologie déjà parfaitement maîtrisée.

## Alternatives Considered

### Node.js

Node.js aurait permis une mise en route rapide, mais la stack retenue a été préférée pour garder une séparation claire entre backend et frontend, ainsi qu’un backend compilé et simple à déployer.

### Python

Python aurait été adapté pour aller vite, mais le projet bénéficie davantage d’un backend compilé, simple à livrer en conteneur, et d’une structure claire pour une API métier.

### Rust

Rust offre de très bonnes garanties techniques, mais sa complexité n’est pas justifiée pour un MVP de 2 semaines.

### React

React aurait été une option viable, mais Angular apporte un cadre plus structuré et plus direct pour une application métier.

### Svelte

Svelte est léger et rapide, mais Angular offre davantage de conventions et de structure pour un projet solo devant rester lisible.

## Notes on Implementation

L’architecture retenue sera organisée de la manière suivante :

- `cmd/api/main.go` comme point d’entrée du backend ;
- `internal/handler` pour les routes HTTP ;
- `internal/service` pour la logique métier ;
- `internal/repository` pour l’accès à la base de données ;
- `internal/middleware` pour l’authentification et les rôles ;
- `internal/model` pour les structures métier ;
- `migrations/` pour le schéma de base de données.

Le frontend Angular sera organisé avec :

- des pages ;
- des composants réutilisables ;
- des services API ;
- une gestion claire des routes et des guards.

## Decision Summary

La stack retenue pour TaskForge est :

- **Backend** : Go avec Gin
- **Frontend** : Angular

Ce choix répond au mieux aux contraintes de délai, de lisibilité, de maintenabilité et de déploiement du projet.
